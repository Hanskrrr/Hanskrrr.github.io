Gallery 的第三层内容采用这样一种做法：作者在自己的电脑上把文章和媒体加密，网站公开提供密文；读者输入口令后，自己的浏览器才恢复出可阅读的内容。

这里最值得理解的不是某个 API 的名字，而是：当网站的代码和文件都能被下载时，为什么仍然可以保密？口令如何变成密钥？浏览器凭什么判断解密成功？成功后的明文又去了哪里？

本文对应 2026-09-24 的项目实现。文中的数据流和参数来自代码；公式用来展开代码调用背后的机制。例子全部是合成内容，不使用真实私密原稿或口令。先沿实际流程理解，再讨论它能保证什么。

隐藏入口解决不了内容泄露

如果一段文章已经以明文放进网页资源，即使没有导航链接，查看资源的人仍然可以读取它。加密要改变的是文件本身，而不只是入口的显示方式。

假设最初写成这样：

if (input === '某个隐藏指令') {
  show(privateArticle);
}

读者的浏览器必须先下载这段代码以及 privateArticle，才能执行判断。访问者可以读源码、检查网络响应，也可以直接修改条件。问题并不在于指令藏得不够深，而在于判断条件与被保护的明文已经一起交给了对方。再加一层函数、压缩代码或把入口换个名字，都不能改变这个事实。

这迫使我们引入一种新的能力：公开文件本身不能包含可直接读取的原稿；恢复原稿还必须依赖一个没有随网站交付的秘密。密码学把这个秘密称为密钥。

Gallery 的三层内容由此形成明确的边界：

先把文章变成字节

字符串、字节数组与对象是不同的东西

假如熟悉 C/C++，可以把 Uint8Array 理解为带有长度的无符号字节数组视图，每个元素的值为 0 到 255。ArrayBuffer 是底层的一段二进制存储，Uint8Array 提供按字节访问它的方法。密码算法处理的是这些字节，不认识“标题”“汉字”或“照片”。

本地加密代码先做：

const source = new TextEncoder().encode(JSON.stringify(content));

这其实有两次转换：

  1. JSON.stringify 把 JavaScript 对象序列化成 JSON 字符串，确定字段、标点和内容的排列。
  2. TextEncoder 把字符串编码成 UTF-8 字节，供加密算法读取。

例如，字符 A 的 UTF-8 是一个字节 41，字符 中 是三个字节 E4 B8 AD，这里使用十六进制表示。JavaScript 的字符串 .length 数的是 UTF-16 码元，不能拿它当 UTF-8 字节长度。这个区别会直接影响文件大小与长度限制。

解密时反着走：字节数组 → UTF-8 字符串 → JSON.parse 得到对象。项目使用 TextDecoder('utf-8', { fatal: true })，遇到非法 UTF-8 就失败，避免悄悄用替代字符继续解析。

Base64 为什么不是加密

JSON 适合保存文本，不能直接容纳任意二进制字节。因此 salt、IV 和密文需要先编码为 Base64 字符串。

Base64 大致把每 3 个字节的 24 个二进制位，分成 4 组，每组 6 位，再查表变成 4 个可打印字符。必要时用 = 补齐。长度为 nnn 字节的数据会得到：

LBase64=4⌈n3⌉L_{\text{Base64}}=4\left\lceil\frac{n}{3}\right\rceilLBase64​=4⌈3n​⌉

任何人知道这套规则就能反向转换，不需要秘密。因此，把文章 Base64 编码再藏到 JavaScript 里，仍然等于公开文章。

操作 输入与输出 是否依赖秘密 在本项目中的用途
UTF-8 编码 字符串 → 字节 否 统一文本的字节表示
Base64 编码 字节 → 可打印文本 否 把二进制放进 JSON
SHA-256 哈希 任意长度字节 → 32 字节摘要 否 PBKDF2 所用 HMAC 的底层哈希

认证加密 明文、密钥、IV、AAD → 密文与标签 密钥是秘密 同时保护内容和检查篡改

哈希也不是可逆编码：它把无限多种可能的输入映射到固定大小的输出，必然有不同输入对应同一输出，因此没有“把哈希值解密回文章”的一般方法。但口令若来自很小的候选集合，攻击者仍可逐个计算并比较；不需要逆转哈希。

从口令得到密钥

口令不是直接用于 AES 的密钥。这个演示使用 PBKDF2，把输入口令、公开的随机盐以及计算参数组合起来，派生出密钥。增加计算成本可以减慢逐个猜测口令的速度，但不能把弱口令变成不可破解的秘密。

为什么不能直接截取口令，或只算一次哈希

AES-256 需要 256 位，也就是 32 字节的密钥。人输入的口令可能很短，也可能含中文。把口令截成 32 字节或在后面补零，只解决了长度问题，没有解决可预测性。

改成 SHA-256(口令)，确实总能得到 32 字节；但 SHA-256 的目标之一就是高效处理数据。攻击者可以给每个常见口令快速算出候选密钥，再尝试解密。我们需要的是：合法读者只做一次可以接受，但对大量候选重复执行时成本明显增加的计算。

PBKDF2 是 Password-Based Key Derivation Function 2，即“基于口令的密钥派生函数”。在本项目中：

P=UTF8⁡(口令)K=PBKDF2⁡HMAC-SHA256(P,S,c,32)c=600000\begin{aligned} P &= \operatorname{UTF8}(\text{口令})\\ K &= \operatorname{PBKDF2}_{\mathrm{HMAC\text{-}SHA256}}(P,S,c,32)\\ c &= 600000 \end{aligned}PKc​=UTF8(口令)=PBKDF2HMAC-SHA256​(P,S,c,32)=600000​

其中 SSS 是 16 字节随机盐，ccc 是迭代次数，最后的 323232 表示输出长度为 32 字节。相同口令、相同盐、相同参数会得到相同密钥；浏览器正是依靠这个确定性重建作者使用的密钥。

盐公开了，为什么仍然有用

设两个文件使用同一口令，如果不加盐，派生结果相同。攻击者为一个常见口令计算出的密钥，就可以拿去尝试所有这些文件，甚至提前制作查找表。

加入每次随机生成的盐后，文件甲需要计算 KA=KDF⁡(P,SA)K_A=\operatorname{KDF}(P,S_A)KA​=KDF(P,SA​)，文件乙需要计算 KB=KDF⁡(P,SB)K_B=\operatorname{KDF}(P,S_B)KB​=KDF(P,SB​)。不同盐通常得到不同密钥；攻击者必须针对不同盐分别做派生。

盐的任务是减少跨文件复用猜测工作和预计算表的收益。它不是另一个口令，也不会让攻击者无法猜一个具体文件的口令。盐必须随密文保存，否则读者无法复现派生过程。RFC 8018 §4 说明了盐和迭代次数的作用。

flowchart TB
  I["口令的 UTF-8 字节<br/>公开盐：16 字节<br/>迭代次数：600000"] --> KDF["PBKDF2<br/>使用 HMAC-SHA-256"]
  KDF --> K[秘密 AES 密钥：32 字节]
  K --> G["AES-GCM 处理文章字节<br/>另加公开 IV：12 字节<br/>以及固定 AAD"]
  G --> O[密文与认证标签]

盐进入上面的派生步骤，IV 进入下面的加密步骤。它们都可以公开，但参与的是不同计算，不能互相替代。

六十万次到底在重复什么

PBKDF2 不是把文章加密六十万遍，也不是简单地连续对口令做六十万遍 SHA-256。它使用 HMAC：一种把秘密与消息组合进哈希计算的构造。在此处，HMAC 的秘密输入是口令字节，输出为 32 字节。

为了看清 HMAC 的组成，令 HHH 表示 SHA-256，QQQ 表示整理成 64 字节的 HMAC 密钥块：口令长于 64 字节时先哈希，然后补零；否则直接补零。则：

HMAC⁡P(X)=H((Q⊕opad)∥H((Q⊕ipad)∥X))\operatorname{HMAC}_{P}(X) =H\bigl((Q\oplus\mathrm{opad})\Vert H((Q\oplus\mathrm{ipad})\Vert X)\bigr)HMACP​(X)=H((Q⊕opad)∥H((Q⊕ipad)∥X))

∥\Vert∥ 表示拼接，⊕\oplus⊕ 表示逐位异或；ipad 和 opad 是由固定字节 0x36 和 0x5c 分别重复组成的 64 字节块。内外两层把秘密混入计算；仅知道消息，不能像普通无密钥哈希那样重新算出合法结果。构造定义见 RFC 2104 §2。

本项目需要 32 字节派生结果，正好等于一个 HMAC-SHA-256 输出块，因此 PBKDF2 只需要生成一个输出块：

U1=HMAC⁡P(S∥INT⁡32(1))Uj=HMAC⁡P(Uj−1),2≤j≤cK=U1⊕U2⊕⋯⊕Uc\begin{aligned} U_1 &= \operatorname{HMAC}_{P}(S\Vert\operatorname{INT}_{32}(1))\\ U_j &= \operatorname{HMAC}_{P}(U_{j-1}),\quad 2\le j\le c\\ K &= U_1\oplus U_2\oplus\cdots\oplus U_c \end{aligned}U1​Uj​K​=HMACP​(S∥INT32​(1))=HMACP​(Uj−1​),2≤j≤c=U1​⊕U2​⊕⋯⊕Uc​​

这里的 INT⁡32(1)\operatorname{INT}_{32}(1)INT32​(1) 是四字节大端整数 00 00 00 01，表示第一个输出块。每个 UjU_jUj​ 都是 32 字节；下一次计算依赖前一次结果，最后逐位异或起来。需要更长派生结果时才会计算更多输出块，不能把“只生成一个块”推广到任意 PBKDF2 用法。公式对应 RFC 8018 §5.2。

单个候选的链式依赖增加了尝试成本，但不同候选仍能在多核或多台设备上并行。六十万次是当前格式的固定参数，不是对所有设备、所有年代都合适的常数，也不是六十万位安全强度。

验证与解密

内容使用 AES-GCM 加密，它同时提供机密性和完整性检查。浏览器尝试用派生的密钥解密；口令错误或者密文被改动时，认证失败，页面不会显示原稿。

要理解“同时提供”，先把这两个要求分开：机密性要求旁观者读不懂内容；完整性要求别人改动内容后，我们能发现并拒绝它。只实现前者，还不足以安全地显示解密结果。

AES 是固定大小的积木，GCM 是使用积木的规则

AES 本身是分组密码。固定密钥 KKK 后，它把一个 128 位输入块变换成一个 128 位输出块，并且可以逆转。AES-256 中的 256 是密钥长度，它每次处理的块仍是 128 位，即 16 字节。

AES 内部把这 16 字节按列放入一个 4×44\times44×4 状态阵列：

[a0a4a8a12a1a5a9a13a2a6a10a14a3a7a11a15]→ EK [b0b4b8b12b1b5b9b13b2b6b10b14b3b7b11b15]\begin{bmatrix} a_0&a_4&a_8&a_{12}\\ a_1&a_5&a_9&a_{13}\\ a_2&a_6&a_{10}&a_{14}\\ a_3&a_7&a_{11}&a_{15} \end{bmatrix} \quad\xrightarrow{\ E_K\ }\quad \begin{bmatrix} b_0&b_4&b_8&b_{12}\\ b_1&b_5&b_9&b_{13}\\ b_2&b_6&b_{10}&b_{14}\\ b_3&b_7&b_{11}&b_{15} \end{bmatrix}​a0​a1​a2​a3​​a4​a5​a6​a7​​a8​a9​a10​a11​​a12​a13​a14​a15​​​ EK​ ​​b0​b1​b2​b3​​b4​b5​b6​b7​​b8​b9​b10​b11​​b12​b13​b14​b15​​​

阵列不是图片坐标，只是一种安排字节的位置的方法。算法反复进行字节替换、行移位、列混合和轮密钥异或，使输入位和密钥位的影响扩散。AES-256 使用 14 轮，最后一轮不进行列混合。具体变换定义见 NIST FIPS 197。

现在遇到新的问题：一篇文章可能有几千字节，而且我们还要检测篡改。单个 16 字节的可逆变换并没有规定如何处理这些要求。工作模式负责规定怎样调用 AES、怎样处理长消息，以及是否提供认证。项目采用的模式是 GCM。

先用异或理解计数器加密

异或的规则是相同为 0、不同为 1。它有一个关键性质：

(M⊕Z)⊕Z=M(M\oplus Z)\oplus Z=M(M⊕Z)⊕Z=M

例如四位的玩具计算中，1010 XOR 0110 = 1100，再算 1100 XOR 0110 就回到 1010。这说明：如果双方能得到同一段别人不知道的字节流 ZZZ，就能用异或完成加密与解密。玩具例子只说明运算关系，不是可使用的密码方案。

GCM 的机密性部分使用计数器模式：由 IV 构造计数器块，再用 AES 把不同计数器块变成密钥流。对第 iii 个明文块：

Zi=EK(Ji),Ci=Mi⊕ZiZ_i=E_K(J_i),\qquad C_i=M_i\oplus Z_iZi​=EK​(Ji​),Ci​=Mi​⊕Zi​

解密时重新生成 ZiZ_iZi​，计算 Mi=Ci⊕ZiM_i=C_i\oplus Z_iMi​=Ci​⊕Zi​。因此在 GCM 内，即使执行的是“解密”，产生密钥流时仍调用 AES 的正向变换。

当前 IV 是 96 位。GCM 从 J0=IV∥031∥1J_0=IV\Vert0^{31}\Vert1J0​=IV∥031∥1 开始，正文第一块使用 J1=inc32⁡(J0)J_1=\operatorname{inc32}(J_0)J1​=inc32(J0​)；inc32 增加末尾 32 位计数器。末块不足 16 字节时只取所需长度的密钥流，正文不需要补到 16 字节倍数。

IV 为什么不能在同一密钥下重复

假设两次加密用了相同的 KKK 和 IV，就会生成相同的密钥流 ZZZ。攻击者把两份密文异或：

C1⊕C2=(M1⊕Z)⊕(M2⊕Z)=M1⊕M2\begin{aligned} C_1\oplus C_2 &=(M_1\oplus Z)\oplus(M_2\oplus Z)\\ &=M_1\oplus M_2 \end{aligned}C1​⊕C2​​=(M1​⊕Z)⊕(M2​⊕Z)=M1​⊕M2​​

秘密的 ZZZ 被抵消了。若攻击者知道一份明文的一部分，就能恢复另一份对应部分；GCM 的认证能力也会受到严重破坏。这不是“密文看起来稍微有些相似”，而是复用了不应复用的密码学状态。

IV 在这里也称 nonce，强调同一密钥下不重复使用。项目每次真正加密时，用 crypto.getRandomValues 分别生成新的 16 字节盐和 12 字节 IV。新盐通常使派生密钥也改变，但我们仍应单独维护“同一密钥不重用 IV”的规则，而不把希望寄托在另一个参数上。随机生成使碰撞概率很小，并不等于数学上的绝不碰撞。

只有异或加密，为什么仍然不够

计数器模式保护了读取，却没有阻止有规律的修改。攻击者不知道明文，仍能把密文改成 C′=C⊕ΔC'=C\oplus\DeltaC′=C⊕Δ；解密便得到 M′=M⊕ΔM'=M\oplus\DeltaM′=M⊕Δ。它可以按选定的位翻转明文，而单纯异或解密不会报警。

因此还需要一个依赖秘密密钥的认证标签 TTT，让接收方检查密文是否匹配。GCM 使用 GHASH 把密文、附加数据和它们的长度组合起来，再与由密钥和 IV 生成的值混合，得到标签。

其核心关系可以写成：

H=EK(0128),T=EK(J0)⊕GHASH⁡H(A,C)H=E_K(0^{128}),\qquad T=E_K(J_0)\oplus\operatorname{GHASH}_{H}(A,C)H=EK​(0128),T=EK​(J0​)⊕GHASHH​(A,C)

这里标签取完整 128 位。式中的 GHASH⁡H(A,C)\operatorname{GHASH}_{H}(A,C)GHASHH​(A,C) 是简写，包含分块、补零以及编码后的 AAA、CCC 位长度，不是直接把两串字符拼起来哈希。

GHASH 中每个块是 128 位，逐块更新形如 Yi=(Yi−1⊕Xi)⋅HY_i=(Y_{i-1}\oplus X_i)\cdot HYi​=(Yi−1​⊕Xi​)⋅H，初值为零。这里的乘法不是普通整数乘法，而是在二元有限域中计算：把位串看作系数为 0 或 1 的多项式，乘积按规定多项式约简，系数相加使用异或。这样，数据及其顺序被聚合进一个 128 位结果。它与 PBKDF2 里的 SHA-256/HMAC 是不同构造，不能混为一谈。

接收方用自己的密钥重新算标签；匹配才交出明文，不匹配则失败。计数器、GHASH、标签和唯一 IV 的正式定义见 NIST SP 800-38D §§6–8。项目把这些运算交给 Web Crypto，没有自己实现 AES 或有限域运算。

AAD：不加密，但必须一致的上下文

AAD 是 Additional Authenticated Data，即附加认证数据。它不需要隐藏，却需要参与认证。例如，一个格式可以把“这是哪个协议版本的数据”绑定到密文上，防止它被误当作其他用途的数据。

项目两端固定使用：

new TextEncoder().encode('gallery-exhibit:v1')

这段 ASCII 文本是 18 字节。它不作为单独字段写入 envelope，而是加密与解密代码共同约定的常量。改变解密端的 AAD，就算口令、盐、IV 和密文都没变，认证也会失败。

这也意味着：当前 AAD 是固定用途标记，不是对整份 JSON 头部的逐字签名。 修改空格或字段顺序，并不会使已解码的密文失效；算法和版本参数由代码显式检查，盐和 IV 则通过密钥派生与 GCM 运算影响认证结果。

  "ciphertext": "<密文 C 与标签 T 拼接后的 Base64>"
}

其中有一个容易遗漏的细节：Web Crypto 的 AES-GCM 加密返回值是 C∥TC\Vert TC∥T。因此 ciphertext 字段虽然只有一个名字，实际携带了正文密文和末尾的认证标签；不需要另找一个 tag 字段。接口约定见 Web Cryptography：AES-GCM。

若 UTF-8 明文长 nnn 字节，当前标签是 16 字节，则：

∣C∣=n,∣T∣=16,∣C∥T∣=n+16|C|=n,\qquad |T|=16,\qquad |C\Vert T|=n+16∣C∣=n,∣T∣=16,∣C∥T∣=n+16

这比“加密后都不可知”更精确：内容被隐藏，但长度大体暴露。文件还会多出 Base64 膨胀和 JSON 头部。

对象 项目中的长度或值 能否随网站公开 作用
口令 PPP 用户输入的 UTF-8 字节 不能 保密所依赖的外部秘密
盐 SSS 16 字节，Base64 后 24 字符 能 区分每次口令派生
迭代次数 ccc 600000 能 规定派生工作量
AES 密钥 KKK 32 字节 不能 实际驱动加解密

公开算法不等于公开秘密。别人可以完整复制解密代码，但仍然缺少正确密钥；如果网站把密钥也一并打包，再成熟的算法也不能补救这个交付方式。

沿项目代码走完一次加密与解锁

作者端：在发布之前加密

当前文章流程由本地 scripts/publish.mjs 处理：公开文章生成网页和公开索引；私密笔记转成文章数据后，合并进展览对象，再调用 scripts/envelope.mjs 的 encryptExhibit。由发布器解析到的 Vault 本地图片附件会内嵌进加密载荷，而不是先发布一个明文图片 URL。手工准备展览 JSON 时，还可以用本地 scripts/encrypt-demo.mjs 包装同一个加密函数。

这里的内嵌处理针对发布器能解析的本地附件；正文中直接写入的外部或站内绝对图片 URL 会保留原地址，不会自动被下载并加密。不能把“私密笔记中的引用”一概当成受保护的附件。

这些脚本是本地开发工具，按项目约定不进入公开仓库；浏览器解密模块才是网站需要发布的代码。

encryptExhibit 的执行顺序是：

  1. 展览对象经 JSON.stringify 与 UTF-8 编码，得到明文字节。
  2. 用安全随机源生成盐和 IV；这里没有使用 Math.random()。
  3. 导入口令材料，执行 PBKDF2，得到可用于加密的 AES 密钥对象。
  4. 传入 IV、固定 AAD 和 128 位标签参数，执行 AES-GCM。
  5. 把盐、IV、C∥TC\Vert TC∥T 转为 Base64，生成 envelope。
  6. 再调用浏览器共用的 decryptPayload，确认封装能解开且内容结构有效，随后返回 envelope。

这个回读检查会发现加密端与解密端的参数不一致，也会拒绝不支持的内容结构；它不是对整个系统的安全证明。

浏览器端：先区分公开命令与口令候选

入口位于 src/terminal/page.js 的 submit。它保存当前输入，然后立即清空输入框及字符镜像。若输入全为空白则返回；否则先交给虚拟 shell。

若是已识别的公开命令，就执行公开命令；若不是，才把原始候选字符串交给 tryUnlock。候选不会经 shell 分词后再拼回，也不在这里转小写或裁掉首尾空格。因此 Abc、abc 和 abc 会产生不同的口令字节。

这里还有几项实际限制：输入控件会移除 CR/LF 换行；能被识别为公开命令的输入不会进入口令分支；输入控件和解密函数都限制长度不超过 1024 个 UTF-16 码元，并非 1024 个 UTF-8 字节。因此不能把“支持任意字符串口令”理解为当前终端 UI 可以无条件输入所有字符串。项目也没有做 Unicode 规范化，视觉相同但编码不同的文本可能产生不同密钥。

tryUnlock 禁用输入，显示“正在检查输入…”，并创建取消控制器。失败时终端只显示统一的“未识别的指令。”，不把候选打印出来，也不把它写入命令历史或 URL。

不保存历史，不等于输入时看不见

当前终端使用 textarea，并把正在输入的字符镜像到 DOM，所以旁观者在输入时可以看见它。这里没有专用的掩码密码框。“不回显”指提交后不加入终端输出记录，不能扩大成“屏幕上从未出现口令”。

获取密文并检查外层格式

unlockExhibit 请求网站的 /data/exhibit.enc.json，使用 cache: 'no-store' 与 credentials: 'omit'，这次请求不携带 Cookie 等凭据，也不包含口令。no-store 不能阻止访问者自己保存公开密文。

取得 JSON 后，readEnvelope 检查固定版本、算法、迭代数、密钥长度、标签长度，以及 Base64 和解码后的长度：

  • 盐必须为 16 字节，IV 必须为 12 字节。
  • C∥TC\Vert TC∥T 至少 16 字节，上限为 16 MiB，也就是 16×1024216\times1024^216×10242 字节。
  • iterations 必须恰好是 600000；它不是任由文件指定一个任意大的计算量。

上限检查发生在响应 JSON 已读入之后，因此它能约束接受的密码学载荷，却不是流式下载大小限制。正文最多比 C∥TC\Vert TC∥T 的上限少 16 字节；解析后的对象和字符串还会占额外内存。

三个关键 Web Crypto 调用

下面是 decryptPayload 的核心调用，省略了外层校验与错误处理；salt、iv 和 ciphertext 此时都已是字节数组：

const material = await crypto.subtle.importKey(
  'raw', new TextEncoder().encode(passphrase),
  'PBKDF2', false, ['deriveKey'],
);

const key = await crypto.subtle.deriveKey(
  { name: 'PBKDF2', hash: 'SHA-256', iterations: 600_000, salt },
  material,
  { name: 'AES-GCM', length: 256 },
  false,
  ['decrypt'],
);

const plaintext = new Uint8Array(await crypto.subtle.decrypt(
  {
    name: 'AES-GCM', iv, tagLength: 128,
    additionalData: new TextEncoder().encode('gallery-exhibit:v1'),
  },
  key,
  ciphertext,
));

importKey 把口令字节包装成供 PBKDF2 使用的 CryptoKey 材料，它自己没有执行六十万次派生。deriveKey 才产生 AES 密钥。decrypt 验证标签并解密，认证失败时 Promise 被拒绝，调用方拿不到成功返回的明文字节。

两个 false 表示密钥不可通过标准导出接口导出；['deriveKey'] 与 ['decrypt'] 限定 API 允许的用途。可以把 CryptoKey 理解为带有算法、权限和内部密钥材料的句柄。不可导出减少直接读取密钥字节的途径，但恶意的同源脚本仍可能读取输入、使用可访问的密钥句柄或窃取解密后的内容。

这些方法返回 Promise。await 暂停当前异步函数的后续逻辑，待计算完成后再恢复，而不是在 JavaScript 主线程手写六十万轮同步循环。它并不让计算免费，也不保证其他解析与渲染步骤不会卡顿。可以联系 理解 JavaScript 事件循环 理解恢复执行的过程。

Web Crypto 的 subtle 接口要求安全上下文。部署通常使用 HTTPS，本机回环地址在标准中属于可被视为可信的开发环境；这不等于任意 HTTP 网站都能使用它。依据见 Web Cryptography 的接口定义 和 Secure Contexts 的可信来源判断。

认证成功之后，还要检查内容能不能用

解密得到字节后，代码继续执行严格 UTF-8 解码、JSON 解析，以及 readExhibit 结构校验。它检查版本、文章与图片数组、字符串长度、媒体 MIME 类型和可选时间线，丢弃未知字段，然后返回新的受支持对象。

这里有两个不同问题：

  • 密码学认证回答“这些字节是否与当前密钥、IV 和 AAD 匹配”。
  • 结构校验回答“这些字节表示的数据是否符合本程序的输入要求”。

持有口令的人可以加密一个不符合展览结构的对象，所以认证成功不能替代结构校验。反过来，一个长得很像合法 JSON 的文件也不能替代密码学认证。

一个可以自己运行的完整例子

下面使用真实的本地加密函数与浏览器共用的解密函数，只输入合成对象。在项目根目录使用支持该项目的 Node.js 环境运行；scripts/envelope.mjs 是本机开发工具，公开仓库的干净克隆不一定包含它。

const content = {

  crypto.getRandomValues(new Uint8Array(32)),
).toString('base64'); // 本次实验随机产生，不打印、不写文件

const json = JSON.stringify(content);

assert.notEqual(second.cipher.iv, envelope.cipher.iv);

解锁之后，明文存在哪里

页面对象与媒体 URL

openExhibit 把解密后的对象放进模块变量 decrypted，再切换到房间界面。它没有设置一个持久的 unlocked=true 标志，也没有把口令、密钥或解密对象写入 localStorage、sessionStorage 或 IndexedDB。网站的主题等其他偏好可以持久保存，不能据此认为解锁状态也被保存。

照片和音频原先以内嵌 Base64 存在于加密对象中。展示时，代码把它们还原成字节，创建 Blob，再用 URL.createObjectURL 生成 blob: URL 供 <img> 或 <audio> 读取。这个 URL 指向浏览器管理的本地资源，不是服务器上的明文附件地址。

“懒创建媒体 URL”只推迟了 Blob 和显示资源的创建；整个展览包早已一次性下载并解密。它并没有实现按照片逐个下载、逐个解密。

私密笔记还有另一条路径：本地渲染好的 html 在解密后插入页面，正文中的内嵌图片可能使用 data: URL。不能把所有解密媒体都描述成 Blob URL。

锁定与取消是两件不同的事

如果用户在派生密钥期间离开页面，计算可能还没完成。不能仅仅隐藏“正在检查”的提示，因为稍后返回的成功结果可能又把房间打开。

项目使用 AbortController 取消尚未完成的网络请求，并在关键位置检查 signal.aborted。Web Crypto 的这次派生和解密调用本身没有接收 AbortSignal 的参数，因此已经开始的计算不能这样中断；unlockExhibit 会在解密结束后再检查一次，丢弃过期结果，tryUnlock 也检查当前视图。

  participant App as 页面与解锁流程

  Note over App: 用户离开<br/>标记已取消

锁定已展示的内容则由 lockContent 处理：销毁房间交互、取消待完成尝试、置空解密对象引用、暂停音频并移除其源、撤销已创建的 Blob URL、清空图片对话框。随后页面渲染替换房间 DOM。导航与 pagehide 都有相应的清理接线。

清理引用不等于安全擦除全部内存

decryptPayload 在 finally 中对自己持有的明文字节数组执行 fill(0)，本地加密端在正常完成加密后也清零 source。这能覆盖对应数组中的字节，却不能逆向清掉此前创建的全部副本。

字符串、JSON.parse 生成的对象、DOM 文本、浏览器内部缓冲以及用户复制的内容，可能已经存在于别处。JavaScript 没有让应用可靠覆写所有字符串副本的接口，垃圾回收的时机也不由此处代码决定。把变量赋成空字符串或 null，只是移除一个引用；撤销 Blob URL，也不是撤销已经被用户保存的照片。

所以这里准确的承诺是：应用不主动持久保存这些秘密，离开时停止展示并释放自己管理的资源。 它没有提供取证级内存擦除，也不能对不可信浏览器或操作系统提供保证。

静态方案的限制

密文仍是公开的，可以被下载后离线尝试口令。已经获得明文的人也可以保存它。没有后端的方案无法可靠地收回对方已经拿到的内容，也无法用一个前端限速按钮阻止离线猜测。

攻击者不需要先拿到一个“口令哈希”

攻击者可以复制同样的流程：猜一个口令 → 根据公开盐执行 PBKDF2 → 用候选密钥做 GCM 认证解密 → 检查是否成功。认证标签已经让他能够验证猜测，不需要另外公开 SHA-256(口令)。

如果额外放置一个快速口令哈希用于“先判断密码对不对”，反而给了攻击者跳过昂贵派生的捷径：先快速筛选口令，只对命中者做真正解密。当前实现没有这样的快速校验表。

设攻击者要尝试 NNN 个等可能候选，每次完整尝试耗时为 ttt，能提供 ppp 份近似独立的并行计算能力，则理想化平均时间为：

T平均≈N2tpT_{\text{平均}}\approx\frac{N}{2}\frac{t}{p}T平均​≈2N​pt​

这只是成本模型：真实口令分布并不均匀，不同硬件速度和并行效率也不同。它说明两件事：增加迭代主要提高 ttt；选择真正难猜的口令主要扩大有效候选空间 NNN。两者都重要。

例如，若口令是均匀随机的六位十进制数，它只有 10610^6106 种可能，约为 log⁡2(106)≈19.9\log_2(10^6)\approx19.9log2​(106)≈19.9 位选择空间。即使最后得到的是 256 位 AES 密钥，攻击者仍然可以沿原本的一百万个口令候选去找；派生不会凭空创造 256 位的秘密。普通人随手想出的六位口令通常更不均匀。

HTTPS、内容加密和可信代码分别负责什么

HTTPS 保护传输过程，并帮助浏览器确认连接的站点；它不会让公开静态资源只对某个读者可读。AES-GCM 让被下载的文件仍然是密文，但读者必须信任执行解密的网页代码。

如果站点或其脚本被替换，恶意代码可以在读者输入时窃取口令，或在成功解密后发送明文。即便密钥设置为不可导出，也无法阻止它读取已经进入 DOM 的文章。因此客户端加密的信任边界仍包括作者的发布电脑、交付给浏览器的代码、浏览器及相关扩展。

认证也不等于作者身份签名：所有持有同一口令的人都能派生密钥，制作新的有效密文。仅凭 GCM 标签，不能区分“原作者加密”与“另一个口令持有人加密”。

这在 HTML 上尤其重要。readExhibit 对 html 只做类型与长度校验，room.js 使用 innerHTML 显示它；当前信任的是站点所有者的本地 Markdown 生成流程，原始 HTML 在该流程中被关闭。AES-GCM 认证不能充当 HTML 消毒器，也不能保证由不可信来源制作的有效密文内容适合直接插入页面。

更新口令、泄露长度和大文件的代价

如果别人保存过旧密文，并知道旧口令，那么把现有文件换成新口令加密的版本，也不能让他忘记旧版本。新口令可以保护重新加密后的版本，却不能撤回已经交付的秘密。

当前单包设计还意味着：密文存在、文件大小、更新频率以及访问资源的行为可见；解锁时需要下载完整包。媒体先变成 Base64 放进 JSON，整个 JSON 加密后又被 Base64 包装，较大的媒体部分仅编码体积就可能接近原始数据的 (4/3)2=16/9(4/3)^2=16/9(4/3)2=16/9 倍，另加头部、标签及其他内容。

设序列化明文为 nnn 字节，固定输出一块的派生工作随迭代次数 ccc 增长，正文加解密、编码和解析大体随 nnn 增长，可以粗略记为：

T≈TKDF(c)+O(n),空间复杂度=O(n)T\approx T_{\mathrm{KDF}}(c)+O(n),\qquad \text{空间复杂度}=O(n)T≈TKDF​(c)+O(n),空间复杂度=O(n)

这里的空间常数可能不小：JSON 文本、Base64、解码数组、明文对象与媒体 Blob 可能同时存在。当前实现没有流式解密，也没有按附件分包。

从简单方案到当前实现，还能怎样演进

下面是按需求推导的工程路线，不是在声称密码学历史严格按这个顺序发生。

当前办法 新问题暴露的不足 所需的新能力与代价
隐藏链接或前端判断 明文早已交付给浏览器 文件本身加密；需要管理秘密
用一次快速哈希生成密钥 候选口令可低成本批量尝试 带盐、可调工作量的口令派生；读者也要等待
仅用计数器模式加密 密文可被修改而不报警 认证标签；必须同时正确管理 IV 和上下文
PBKDF2 增加计算轮数 攻击者可并行跑许多低内存候选 内存困难派生算法增加内存成本；实现和设备负担也增加
单个加密大包 首次解锁要下载、解析全部内容 加密索引加独立附件；要管理每个附件的 nonce、认证关系与版本
所有人共享一个口令 无法独立撤销某位读者，也不能区分身份 账号授权或按接收者封装密钥；需要额外的身份、密钥或服务器管理

例如 Argon2id 所属的 Argon2 系列把内存资源也纳入成本设计，目的不只是“再多循环几次”。相关机制见 RFC 9106。Gallery 当前仍使用 PBKDF2，没有实现 Argon2id、独立附件加密或多人权限。 是否迁移，需要结合浏览器实现、移动设备负担、格式兼容与维护成本评估，不能只替换算法名称。

无论采用哪种结构，公开前就应完成加密。先把原稿提交到公开 Git 历史，再在构建时加密，无法收回已经公开的原稿。项目的本地发布与泄漏检查脚本用于检查已知私密内容是否混入公开产物；这种检查依赖已有原稿和匹配规则，不等同于发现所有可能的泄露。

回到代码与整个网站

现在可以把全程压缩为两条对应关系：

作者：K=KDF⁡(P,S),(C,T)=Enc⁡K(IV,M,A)读者：K′=KDF⁡(P′,S),M 或失败=Dec⁡K′(IV,C,T,A)\begin{aligned} \text{作者：}\quad K&=\operatorname{KDF}(P,S),\quad (C,T)=\operatorname{Enc}_K(IV,M,A)\\ \text{读者：}\quad K'&=\operatorname{KDF}(P',S),\quad M\ \text{或失败}=\operatorname{Dec}_{K'}(IV,C,T,A) \end{aligned}作者：K读者：K′​=KDF(P,S),(C,T)=EncK​(IV,M,A)=KDF(P′,S),M 或失败=DecK′​(IV,C,T,A)​

前面的文字解释了这里的每个符号来自哪里、哪些能公开、哪些必须保密，以及“解密成功”之后还需要哪些应用逻辑。密码学负责从秘密构造读取能力，网站代码负责获取数据、校验结构、展示结果与清理状态。

继续阅读实际实现时，可以按下面的顺序跳转。浏览器源码链接固定到本次核查的提交，避免以后代码变化使描述失去依据；本地脚本只列文件名，不假装它们已公开。

文件与入口 阅读时重点观察
本地 scripts/publish.mjs 公开、草稿与私密笔记如何分流，私密附件如何内嵌
本地 scripts/envelope.mjs → encryptExhibit 序列化、随机参数、派生、加密与回读校验
terminal/page.js → submit、tryUnlock 输入如何进入解锁分支，哪些内容不会写入历史
vault/crypto.js → readEnvelope、decryptPayload、unlockExhibit 参数校验、三个 Web Crypto 调用、统一失败与取消检查
vault/exhibit.js → openExhibit、lockContent 明文引用、Blob URL 和清理
vault/room.js → mountRoom 文字、HTML、图片与音频如何进入 DOM

可以用三个问题检验自己是否已经把这些关系连起来：为什么盐能公开而密钥不能？为什么同一密钥下重用 IV 会让密文之间泄露关系？为什么锁定页面不能撤回别人保存的文章？若其中某一步还不清楚，可以从对应的公式或函数继续向下拆解。
